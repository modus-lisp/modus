# W32: native 32-bit words on the 30-bit targets — design note and report

The spec is `docs/w32-spec.md`.  This file is what the work leaves behind: what
was built, every deviation from the spec's section 4 and why, the census, and
the numbers.  It grows one section per milestone.

## M0 — baseline (before any change)

Measured on the tree at `cd7d1ec5` (the commit that adds the spec), from a
snapshot copy with vessel at the pinned `c961cb6`.  Nothing in the compiler,
runtime or translators was touched.

### How it is measured

- **Source.** `test/w32-bench.lisp`: local copies of natrium's SHA-256
  compression function and ChaCha20 round core (natrium `cde4e44`), plus
  drivers.  It is portable CL, so the same file is SBCL's reference and the
  Modus benchmark.  `test/w32-bench-check.lisp` checks the copies against
  natrium on SBCL at every padding boundary, and the outputs against FIPS 180-2
  ("abc"), Python hashlib (the `(i*7+3) mod 256` pattern of
  `test/crypto-sha-vectors.lisp`, 1 KiB / 64 KiB / 4 MiB) and RFC 8439 2.3.2:
  39 checks, all pass.
- **Into the images.** `MODUS_EXTRA_SOURCE=test/w32-bench.lisp` compiles the
  file into a CLI image with the BUILD-TIME compiler (AOT), on all three 32-bit
  CLIs (`build-riscv32-cli`, `build-arm32-cli`, `build-i386-cli`) — so i386
  needed no new mechanism (spec 9.2 asked to find or add one: it exists).  The
  functions are homed in MODUS-INT, so they are called as
  `(modus-int::w32b-run KB KB)`.
- **Throughput.** `test/run-w32-bench.sh IMGDIR [REPS] [KB]`: every arch x
  rep in parallel under qemu-user, each run's output lines compared with SBCL's
  for the same sizes (a mismatch fails the script), median of the in-image
  clock (`get-internal-real-time`, which is `clock_gettime` on the hosted
  CLIs).  Run with `NATRIUM_DIR=` when the tree is not in the kiln workspace.
- **X25519.** On no 30-bit HOSTED image today: the 32-bit CLIs bake no SSH
  crypto (`build-cli-common.lisp` links `net/crypto*.lisp` for x64 only, and
  `net/crypto.lisp` needs arch adapters only hosted x64 and the bare images
  define).  The one X25519 that runs on a 30-bit target is
  `net/crypto-32-fast.lisp` in the bare-metal i386 SSH image — exactly what M4
  replaces.  `test/w32-x25519-bare.py IMAGE N` boots it
  (`MODUS_NET_BUILD=1 MODUS_SSH_BUILD=1 build-i386-cl-repl`, no autostart),
  runs RFC 7748 5.2 vector 1 once as the check and N times timed.
- **Instruction counts.** This qemu (7.2) has no TCG plugins, and the spec's
  `-singlestep -d exec` logs one line per guest INSTRUCTION -- the CLI's boot
  alone is 10.4 billion, so six such runs had not finished booting after 30
  minutes and were stopped.  Instead `-d in_asm,exec,nochain`: `in_asm` prints
  each translation block's instructions once, `exec` one line per block
  EXECUTED (`nochain` makes every execution print), and `test/w32-tbcount.c`
  (`gcc -O2`) reads the log from a pipe -- no trace file -- and sums, over
  executions, the instruction count of the block's latest translation.  Run
  for `(w32b-blocks N)` / `(w32b-chacha-blocks N)` at N = 0, 4, 8, six in
  parallel (~38 minutes each); per block = the difference / 4, and the two
  differences check linearity.  Every run's value was checked against SBCL's.

### Found while measuring (not fixed here)

- **Bare-metal i386's `GET-INTERNAL-REAL-TIME` does not advance.**  Five
  X25519s (7.3 s of host time) read as 0 us.  It is `(rdtsc)` divided by
  `(cntfrq)` (`build-cl-repl-common.lisp`); a zero or absent frequency makes it
  return 0.  Not a W32 issue; the X25519 timing uses the host clock.
- **ChaCha20 is 11x slower than SHA-256 on x64 Modus** (SBCL: 4x), and the
  difference is the rotate.  natrium's ChaCha20 rotate is an INLINE FUNCTION
  (`rotl32 (x n)`); Modus's inliner binds the parameters with a LET, so
  `(ash x (- n 32))` has a variable count.  SHA-256's rotate is a macro and its
  counts stay constant.  Consequence for M3 (spec 4.5): rotate recognition only
  sees natrium's ChaCha20 if constant arguments are propagated into an inlined
  body.  Record, then decide in M3.

## M1 — the compilation's target (compiling-for, not running-on)

### What was built

- **`COMPILE-TARGET`** (struct, `mvm/compiler.lisp`), made by
  `MAKE-COMPILE-TARGET-FOR` (`mvm/target.lisp`) from the target struct alone:
  word size, fixnum width and every derived width, big-endian, soft-float
  (a build knob, so the caller passes it), has-fpd, `w32-capable` (NIL until
  M2/M3), the MV slot addresses, the tags, T and NIL.
- **`*COMPILE-TARGET*`**, set by `BUILD-IMAGE` for the whole compilation, with
  a lexical save, `SETQ` and `UNWIND-PROTECT` -- not a special `LET`, which in
  an image does not reach callees (build-modus-selfhost.lisp, the #210
  `:into-buf` note).  `NIL` means "the machine this runs on".
- **The `CT-` readers** (34, `mvm/compiler.lisp`): the field of
  `*COMPILE-TARGET*`, or the running-on constant when none is bound.  They are
  zero-argument calls, not arithmetic forms (+FIXNUM-SIGNED-BITS+'s note).
- **`SET-TARGET-FIXNUM-BITS-FOR`** now makes the descriptor, sets the host
  parameters FROM it and returns it; **`WIDTH-CONSTANTS-SOURCE`** formats the
  descriptor, so a child build's injected widths are the child's.
- **Compile-time evaluation runs for here.**  An in-image static build reaches
  `EVAL` for DEFCONSTANT initforms, EVAL-WHEN and macro expanders; that code
  RUNS in the building image, so `%MVM-EVAL-FORMS-NESTED-IN-STATIC-BUILD` and
  `%EVAL-EXPANDER-RUNTIME` set `*COMPILE-TARGET*` to NIL around it (and restore).
- **CHECK I** (`build-checks.lisp`): no compiler-side file names a running-on
  width constant.  Compiler-side = `compiler.lisp`, `cross.lisp`,
  `translate-riscv.lisp`, `translate-aarch64.lisp`, `translate-x64.lisp` (the
  files whose code is the compiler in modus-sh).  READ, not grepped, so
  comments and docstrings are free; exempt: a name's own DEFVAR/DEFPARAMETER
  and `DEFUN CT-*`.  **Negative control:** `+fixnum-max+` put back into
  `%LIT-BN-LO` fails the load with
  `mvm/compiler.lisp: +FIXNUM-MAX+ in defun %lit-bn-lo -- use its CT- reader`.
- **CHECK J** (`build-checks.lisp`, host-only): for each of the 11 registered
  targets, every host width parameter equals the descriptor's field.
- **The RV32 DDC**: `translate-riscv.lisp` (truncated at
  `install-riscv-translator`), `boot-linux-i386.lisp` and
  `boot-linux-riscv32.lisp` baked into modus-sh; `%INIT-RISCV32-TRANSLATOR`
  (the co-init) and `*TARGET-RISCV32*` in the target co-init;
  `modus-sh --compile-riscv32`; `test/ddc-riscv32-host.lisp` (SBCL twin);
  `test/run-riscv32-ddc.sh`; in `scripts/acceptance-gate.sh` beside the
  AArch64 DDC (run concurrently with it; `MODUS_GATE_NO_DDC` skips all three).

### Deviations from spec section 4.1

- **The readers live in compiler.lisp, not target.lisp.**  First cut put them
  in target.lisp; the x64, i386 and RV32 CLIs bake `compiler.lisp` but NOT
  `target.lisp`, so their runtime compiler called 34 undefined functions.
  The build did not fail -- it stubs unresolved calls to NIL and only prints
  the count (27 -> 147 calls) -- and `(+ 1 2)` still evaluated; compiling a
  bignum literal then died with TYPE-ERROR.  From then on the unresolved-call
  count, base vs new, is part of every check here (it is back to base:
  x64 27/18, aarch64 50/41, rv32 23/12).
- **The host-vs-descriptor agreement check is a build check, not an assertion
  in `SET-TARGET-FIXNUM-BITS-FOR`**: in modus-sh that function runs too, its
  SETFs cannot change folded constants, and the assertion fired on the first
  `--compile-riscv32`.
- **Only the translators baked into modus-sh are compiler-side.**  i386, PPC,
  arm32 and 68k translators still read the host parameters directly: they run
  only on the host, where those are set per build.  When a translator is baked
  into modus-sh, add it to `*GCK-COMPILER-SIDE-FILES*` and CHECK I lists what
  to change.

### What the RV32 DDC found before it passed

Each of these is a way a self-hosted compiler goes wrong only when it builds
for a target narrower than itself, so neither existing DDC could see it:

1. **Boot constants looked up by name.**  `RV-HOSTED-HEAP-GEOMETRY` and
   `RV-HOSTED-ROOT-BLOCK-END` read `+LINUX-RISCV32-HEAP-ADDR+` & co. with
   `FIND-SYMBOL`/`BOUNDP`/`SYMBOL-VALUE` (on the host the translator loads
   before the boot files).  In an image a DEFCONSTANT has no symbol value; the
   translator gave up -- `native 0`, a 3.5 MB image of constant pool.  Fixed in
   the BAKED copy only (build-modus-selfhost.lisp): the values are read from
   the boot file's own DEFCONSTANT forms at bake time and substituted.
2. **Constants defined after their use.**  `+RV-LINUX-SYS-READ+/-WRITE+/-EXIT+`
   were at the end of translate-riscv.lisp; the image's compiler folds a
   constant only after compiling its DEFCONSTANT, so every hosted RV32 trap it
   compiled loaded garbage into a7 (`lui a7,0x6f568` for `li a7,64`; the
   image segfaulted).  Moved to the top of the file (host output unchanged),
   and **CHECK K** now fails the build if any compiler-side file uses a
   constant above its DEFCONSTANT -- negative control: the three put back at
   the end fail the load, naming all three.
3. **Bignum literals decomposed by this image's limbs.**  In-image,
   `float-slot-overrides.lisp`'s `%LIT-*` read a literal's bignum SLOTS (the
   compiled LOGAND on a bignum is a raw AND).  For a 30-bit target a literal
   can be a fixnum HERE (+FIXNUM-LIMIT+ = 2^30: `The value 0 is not of type
   (INTEGER 0 -1)`, the init thunk silently dropped) or a bignum with 62-bit
   limbs where the target wants 30.  Now: same width -> the slot readers,
   exactly as before; different width -> the target's limbs, extracted from
   this image's limbs with fixnum-only arithmetic (fields <= 31 bits from
   62-bit limbs).
4. **The RV code buffer was a generic vector.**  8 bytes per byte on a 64-bit
   host; doubling took ~36 MB of RV32 code to a 512 MB vector.  Bisected by
   input size: every prefix of the dump up to 90% (22 MB native) compiled,
   the whole dump segfaulted.  Now an octet vector (every store is a byte);
   host output unchanged (riscv32 same-source image and riscv64 rungs
   byte-identical).

### Results

- **RV32 DDC: FIXPOINT.**  SBCL and `modus-sh --compile-riscv32` emit the same
  35 MB image from the UEFI DDC's 8.9 MB dump (md5 `6a5f7268...`),
  in 127 s.  **Its negative control fails, as it must:** with
  `COMPILE-INTEGER`'s fixnum-range test put back on the running-on constants
  (CHECK I disabled for that one build), the two images DIFFER -- modus-sh's
  is 40 KB smaller, every literal in [2^29, 2^62) compiled as a fixnum.
- UEFI DDC and AArch64 DDC: PASS (both trees, real and control).
- **C1, same source, both compilers.**  The base x64 CLI's full source
  (8.9 MB, `MODUS_DUMP_FULL_SOURCE`) compiled by the base and the new compiler:
  x86-64, i386 and riscv32 images byte-identical.  Every arch-ladder rung on
  all eight bare back ends (x86-64, aarch64, i386, riscv64, ppc64, ppc32,
  68k, arm32): byte-identical, 35/35 (aarch64 30/30; five rungs fail to build

  `scripts/irdiff.py` (per-function IR, base vs new builds of the CLIs, with
  the GV cache map `MODUS_IR_DUMP` now writes) is the per-function view; the

- Unresolved-call counts unchanged: x64 27/18, aarch64 50/41, rv32 23/12.

## M2 — the opcodes (in progress)

- **ISA** (`mvm/mvm.lisp`): 22 W32 opcodes in free slots #x69-#x6F, #x73-#x7F,
  #x84-#x85, with encoders.  `w32-load`/`w32-store`'s Vaddr holds a RAW
  address, as `:load`'s does (the spec says "untagged Vaddr"; the compiler
  untags with `:shr` first, so each translator reuses its raw-address code).
- **Interpreter** (`mvm/interp.lisp`, the oracle): a W32 register holds the
  Lisp integer in [0, 2^32) -- stored with SVREF, a value the collector
  traces -- and each opcode is defined on that value (`%W32-BINOP`,
  `%W32-UNOP`, `%W32-SHIFT`).  One CASE clause per opcode (no multi-key
  clauses in the interpreter, which the image compiles).
- **Capability**: `COMPILE-TARGET-W32-CAPABLE` is T for :i386 :riscv32 :arm32
  :68k only; its running-on twin `+TARGET-W32+` (0/1) is injected with the
  width constants, so a 32-bit image's own compiler knows its answer.  (One
  more injected constant in every image: a content change, not a change to
  what the compiler emits for a given source.)
- **The test intrinsic** `(%W32 TREE)` (`COMPILE-W32`): a W32 expression tree
  compiled straight to W32 opcodes.  Leaves are variables and fixnum literals
  only, so a tree is free of calls and allocation by construction (C3 needs
  no analysis here).  An error, not a fallback, on a non-capable target.
- **RV32** (`RV-TRANSLATE-W32`): one instruction per op (plus a tag shift
  for fixnum results; `rotl` = SRLI + SLLI + OR, the right half first because
  the source may be the t0 scratch).  Added `RV-EMIT-SLTU`.  On RV64 a W32
  opcode is a recorded gap (`rv-note-unimpl`) and traps.
- **Rungs** `test/w32-rungs/w01..w06` (separate from `test/arch-rungs/`
  because the arch ladder runs every rung on every arch and these must not
  compile for a 64-bit one).  Each answers a bitmask, one bit per check:
  add/carry, mul/mulhu, shr vs sar, rotl 1/16/31/0, the halves / from-fix /
  bitwise ops, load/store byte order.  **riscv32 hosted: 6/6 PASS**, the
  positive control answering WRONG.
- **Found on the way (pre-existing, not W32):** in a CLEAN image, arithmetic
  past ~2^28 and a `:u32` MEM-REF on a 30-bit target call runtime helpers
  the image does not have (GENERIC-ADD; the promoting :u32 path), so the call
  lands on offset 0 -- reproduced on the base tree.  w06 uses literal
  addresses and :u8 reads.
