# W32: native 32-bit words on the 30-bit targets — design note and report

The spec is `docs/w32-spec.md`.  This file is what the work leaves behind: what
was built, every deviation from the spec's section 4 and why, the census, and
the numbers.  It grows one section per milestone.

## M0 — baseline (before any change)

Measured on the tree at `cd7d1ec5` (the commit that adds the spec), from a
snapshot copy with vessel at the pinned `c961cb6`.  Nothing in the compiler,
runtime or translators was touched.

### How it is measured

- **Source.** `test/w32-bench.lisp`: local copies of natrium's SHA-256
  compression function and ChaCha20 round core (natrium `cde4e44`), plus
  drivers.  It is portable CL, so the same file is SBCL's reference and the
  Modus benchmark.  `test/w32-bench-check.lisp` checks the copies against
  natrium on SBCL at every padding boundary, and the outputs against FIPS 180-2
  ("abc"), Python hashlib (the `(i*7+3) mod 256` pattern of
  `test/crypto-sha-vectors.lisp`, 1 KiB / 64 KiB / 4 MiB) and RFC 8439 2.3.2:
  39 checks, all pass.
- **Into the images.** `MODUS_EXTRA_SOURCE=test/w32-bench.lisp` compiles the
  file into a CLI image with the BUILD-TIME compiler (AOT), on all three 32-bit
  CLIs (`build-riscv32-cli`, `build-arm32-cli`, `build-i386-cli`) — so i386
  needed no new mechanism (spec 9.2 asked to find or add one: it exists).  The
  functions are homed in MODUS-INT, so they are called as
  `(modus-int::w32b-run KB KB)`.
- **Throughput.** `test/run-w32-bench.sh IMGDIR [REPS] [KB]`: every arch x
  rep in parallel under qemu-user, each run's output lines compared with SBCL's
  for the same sizes (a mismatch fails the script), median of the in-image
  clock (`get-internal-real-time`, which is `clock_gettime` on the hosted
  CLIs).  Run with `NATRIUM_DIR=` when the tree is not in the kiln workspace.
- **X25519.** On no 30-bit HOSTED image today: the 32-bit CLIs bake no SSH
  crypto (`build-cli-common.lisp` links `net/crypto*.lisp` for x64 only, and
  `net/crypto.lisp` needs arch adapters only hosted x64 and the bare images
  define).  The one X25519 that runs on a 30-bit target is
  `net/crypto-32-fast.lisp` in the bare-metal i386 SSH image — exactly what M4
  replaces.  `test/w32-x25519-bare.py IMAGE N` boots it
  (`MODUS_NET_BUILD=1 MODUS_SSH_BUILD=1 build-i386-cl-repl`, no autostart),
  runs RFC 7748 5.2 vector 1 once as the check and N times timed.
- **Instruction counts.** This qemu (7.2) has no TCG plugins, and the spec's
  `-singlestep -d exec` logs one line per guest INSTRUCTION -- the CLI's boot
  alone is 10.4 billion, so six such runs had not finished booting after 30
  minutes and were stopped.  Instead `-d in_asm,exec,nochain`: `in_asm` prints
  each translation block's instructions once, `exec` one line per block
  EXECUTED (`nochain` makes every execution print), and `test/w32-tbcount.c`
  (`gcc -O2`) reads the log from a pipe -- no trace file -- and sums, over
  executions, the instruction count of the block's latest translation.  Run
  for `(w32b-blocks N)` / `(w32b-chacha-blocks N)` at N = 0, 4, 8, six in
  parallel (~38 minutes each); per block = the difference / 4, and the two
  differences check linearity.  Every run's value was checked against SBCL's.

### Found while measuring (not fixed here)

- **Bare-metal i386's `GET-INTERNAL-REAL-TIME` does not advance.**  Five
  X25519s (7.3 s of host time) read as 0 us.  It is `(rdtsc)` divided by
  `(cntfrq)` (`build-cl-repl-common.lisp`); a zero or absent frequency makes it
  return 0.  Not a W32 issue; the X25519 timing uses the host clock.
- **ChaCha20 is 11x slower than SHA-256 on x64 Modus** (SBCL: 4x), and the
  difference is the rotate.  natrium's ChaCha20 rotate is an INLINE FUNCTION
  (`rotl32 (x n)`); Modus's inliner binds the parameters with a LET, so
  `(ash x (- n 32))` has a variable count.  SHA-256's rotate is a macro and its
  counts stay constant.  Consequence for M3 (spec 4.5): rotate recognition only
  sees natrium's ChaCha20 if constant arguments are propagated into an inlined
  body.  Record, then decide in M3.
